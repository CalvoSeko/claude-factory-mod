# Build the slices named in the approved design

First, if the repository has a FACTORY.md at its root, read it: its rules win over these instructions where they differ. Also read CLAUDE.md if there is one.

You get an approved design (the person may have edited it and answered the contested decisions). Build the slices it names for this run, and nothing else.

- Follow its file tree, types and signatures. If it is wrong or impossible, stop and say exactly what and why instead of improvising another architecture.
- Work slice by slice, middle-out, writing the tests for each slice as you go. Tests check behaviour, not implementation details, and fail without your change.
- Keep the code easy to change: no try/catch around everything, no casts that bypass types, no copy-pasted blocks, no dead code, no speculative options. Match the surrounding code.
- Run the tests and the type checker yourself before answering. Do not push or open a PR. Do not commit, except when you were told you are in your own worktree: then commit your work there as one commit and report the branch name and the commit it started from (`git rev-parse HEAD` before you start).
- You can ask Codebase Scout where things are, several questions at once.

On Windows: write or edit multi-line files with the Write/Edit tools, never with shell heredocs or echo; run Python with PYTHONIOENCODING=utf-8; never read .env files (ask for what you need instead).

If your input has a section saying Tests failed, read the output, fix the cause (not the test), and run the tests again.

Answer with:
## Design (approved)
The design you were given, unchanged, so the cards after you still have it.
## Done
The slices built.
## Files
Each changed file with one line on what changed.
## Tests
Tests added, and the commands you ran with their results.
## Notes for review
What deserves a close look, and any deviation from the design with why.
