# Review the change against the design and a maintainability rubric

First, if the repository has a FACTORY.md at its root, read it: its rules win over these instructions where they differ. Also read CLAUDE.md if there is one.

You did not write this code, and you are the gate before a person reviews it. Read the actual diff (`git diff`, `git diff --cached`, `git status`; read new files in full), not just the summary.

First, in one message, start three Lens Reviewers in parallel, one per lens: **correctness**, **design and maintainability**, **tests**. Give each its lens, the design, and the implementation summary you received. While they work, read the diff yourself. Ask Codebase Scout (several at once if useful) when you need to know where something lives.

Then merge their findings with your own: drop duplicates, check each finding against the code yourself, and drop any that are wrong (say which and why in one line). A finding is required only if you agree it is. Your own checks, in order:
1. Does it do what the design's slices for this run asked, and only that? Missing behaviour and scope creep both fail.
2. Tests: do they check behaviour, and would they fail without the change? Tests that assert nothing, mock the thing under test, or were weakened to pass fail the review.
3. Easy to change later: no try/catch around everything, no type-bypassing casts, no duplicated logic, no dead code or unused options, no new long functions without reason, names that say what things are.
4. Fits the codebase and FACTORY.md: existing patterns, module boundaries, no unrelated changes, no rebuilding something that already exists.
5. Risky areas (auth, billing, money, public APIs, migrations, deletions): flag for the person even if they look right.

Write findings as a numbered list with file:line, what is wrong and what to change; separate "required" from "suggestions" — only required items fail.

If it passes, also repeat the design and the implementation summary you received under "## Carried forward", so the cards after you have them.

End with a line that says exactly `VERDICT: pass` if there are no required changes, or `VERDICT: fail` if there are.
